# 一、本轮核心决策

系统长期目标仍然是多源特征中心，但本轮不把所有数据源做成每个模型的必经流水线。必须采用“确定性优先、按需升级”的分层执行策略：

```text
原生CAA设计语义
        ↓
STEP精确B-Rep + eAAG确定性分析
        ↓
确定性结果完整且无冲突？
    ├─ 是：直接形成Feature Center结果，不渲染、不调用视觉模型
    └─ 否：记录视觉复核请求或人工复核请求
             ↓
       后续阶段才生成局部证据包并按需调用视觉模型
```

本轮必须把“无需视觉即可完成”的主链做完整，并把未来视觉辅助的触发、输入、输出、缓存和回链边界定义清楚；不得把截图生成或远程视觉调用塞进默认路径。

必须遵守以下权责边界。

## 0. 代码质量与中文注释

新增或修改的核心接口、所有权、算法步骤、坐标变换、容差来源、失败降级和非显然判断必须有准确的中文注释。

注释必须解释“为什么”和边界条件，不得把代码逐字翻译成注释，不得用大段过期设计说明替代可读代码。公共JSON字段和协议名称保持英文，解释文档与代码注释使用中文。

## 1. 原生CAA语义

适合读取：

* Hole、Pad、Pocket、Rib、Stiffener等原生设计意图；
* 原始设计参数；
* Feature Tree关系；
* update/stale状态；
* 内部名、显示名和别名。

原生语义不得被视觉推理覆盖或篡改。

## 2. STEP/B-Rep

STEP解析后的精确B-Rep是几何测量和拓扑定位的权威来源，负责：

* Face、Edge、Wire、Shell、Solid；
* 曲面类型；
* 面积、长度、体积；
* 圆柱轴线和半径；
* 局部厚度；
* 曲率；
* 凹凸关系；
* 面邻接图；
* 开口环；
* 型腔深度；
* 岛屿拓扑；
* Feature–Face关系；
* Face–Mesh关系。

所有最终毫米、平方毫米、立方毫米、角度和世界坐标值必须由B-Rep计算，不得直接从截图像素估算。

## 3. eAAG几何推理

eAAG（扩展属性邻接图）是STEP/B-Rep复杂特征推理的核心中间表示，不是普通Face邻接表。它负责把精确几何组织成可查询、可验证、可追溯的图：

* Face、Edge、Wire/Loop、Shell、Solid等拓扑实体及归属；
* 共享边邻接、凹凸、相切连续、包含、同轴、平行、相对、近邻等关系；
* 几何属性、拓扑指纹、空间索引和容差；
* Native Feature与B-Rep Face的候选匹配证据；
* 后续筋条/腹板、型腔/岛屿、自由曲面区域识别所需的公共图查询能力。

本轮必须真实构建、序列化并测试eAAG；不得只在文档里画图或仅输出`adjacent_face_ids`。

## 4. 视觉辅助的长期边界

视觉模型未来只负责：

* 对确定性算法已经发现的疑难候选进行类别消歧；
* 提示候选Face集合可能遗漏或误选的区域；
* 判断是否需要局部放大、剖切或补充视图；
* 返回候选类型、归一化区域和分类/定位置信度。

视觉模型不得：

* 对每个上传模型默认运行；
* 代替B-Rep遍历所有Face；
* 直接给出权威毫米、面积、体积、角度或世界坐标；
* 直接修改Canonical Feature或Feature–Face归属；
* 覆盖CAA原生事实；
* 在低置信度时强行分类。

本轮只实现视觉复核路由协议、触发判定、缓存键和请求记录，不实现真实远程VLM调用，不要求生成完整多视图证据包。

## 5. 融合层

融合层负责：

* 将CAA原生Observation与B-Rep/eAAG Observation合并；
* 对Native Hole候选使用B-Rep规则验证并定位真实Face；
* 保留冲突；
* 形成Canonical Feature；
* 对无法可靠确认的对象输出unknown或needs_review；
* 不得为了提高命中率强制分类。

未来视觉Observation必须沿用同一融合协议接入，但本轮不得用Mock视觉结果冒充实际识别能力。

# 二、总体架构要求

不得把OpenCascade、FreeCAD、图像渲染或视觉模型SDK直接塞进CATIA R21的32位CAA进程。

采用进程隔离：

```text
CAA R21 Worker（VS2008/C++03/x86）
    ↓
原生解析结果 + STEP文件 + Manifest
    ↓
Feature Center Sidecar（现代进程）
    ├─ STEP/B-Rep解析
    ├─ eAAG构建与几何计算
    ├─ 轻量化Mesh生成
    ├─ Native Hole几何定位与验证
    ├─ Visual Review路由协议（默认禁用）
    └─ 多源融合
    ↓
Feature Center Bundle
    ↓
轻量化Web展示/后续API
```

CAA进程继续保持：

* VS2008；
* C++03；
* x86；
* 不依赖Python；
* 不依赖OpenCascade外部版本；
* 不依赖视觉模型；
* 单对象失败隔离；
* 只读打开CATPart；
* 正常关闭文档；
* 无CNEXT/CATSTART残留。

Sidecar可以使用现代C++或Python，但必须根据本机真实环境和仓库结构选择，优先复用已安装的FreeCAD/OpenCascade能力。

不要为了形式统一而强行使用C++03实现现代算法。

Sidecar必须提供可脚本调用的稳定入口。命令名称可以根据仓库现状调整，但至少具备等价能力：

```text
feature-center build
  --native-bundle <CAA输出目录，可选>
  --step <STEP文件>
  --output <任务输出目录>
  --visual-review-mode disabled
  --tolerance-profile <配置>

feature-center validate
  --bundle <Feature Center Bundle目录>

feature-center inspect
  --bundle <Feature Center Bundle目录>
  --feature-id <FC...>
```

要求：

* 参数缺失、文件不存在、Schema不兼容和单位未知时返回非0退出码；
* 对象级可降级问题写Diagnostic，但Bundle级结构损坏必须失败；
* 输出先写任务临时目录，全部校验通过后再发布，失败不得留下看似完整的半成品Bundle；
* 重跑同一任务不得依赖上一次未完成的临时文件；
* stdout/stderr提供可定位的阶段和错误码；
* 日志不输出密钥、完整模型二进制或超长JSON；
* CAA Worker和Sidecar分别有独立退出码、日志和Manifest状态，不能把其中一个成功冒充全链成功。

# 四、先修复现有Decoder扩展协议

现有扩展协议约完成70%。本轮先补齐以下问题。

## 1. Native Capability不得继续Hole专用化

现有类似：

```cpp
GetNativeHoleView()
```

的接口会导致每增加一种原生特征都修改中央`INativeObjectView`。

改造成C++03兼容的通用Capability机制，例如：

```cpp
class INativeCapabilityView
{
public:
    virtual ~INativeCapabilityView() {}
    virtual const char* GetCapabilityId() const = 0;
};

class INativeObjectView
{
public:
    virtual const INativeCapabilityView* FindCapability(
        const char* capabilityId) const = 0;
};
```

`INativeHoleView`可以继承`INativeCapabilityView`，但中央Object View不得再为每种特征新增一个Getter。

实际设计可根据现有代码调整，但必须达到：

* 新增一种Capability不修改Crawler；
* 不修改`INativeObjectView`公共方法列表；
* API无关Core不引用CATIA头文件；
* 不依赖C++11；
* 生命周期和所有权清晰。

## 2. Typed Payload承载不得继续Hole专用化

`FeatureRecord`不得不断增加：

```text
has_native_hole
native_hole
has_native_pad
native_pad
has_native_pocket
native_pocket
...
```

建立C++03兼容的可扩展Typed Payload边界。

可以采用：

* 抽象Payload基类；
* 明确的Payload Type ID；
* Clone/所有权协议；
* 通用字段写入接口；
* Payload自身序列化接口；
* 其他安全的C++03实现。

但必须同时满足：

* 每种特征仍有独立强类型数据结构；
* 不能全部退化成无约束字符串Map；
* JSON Writer不需要为每一种新Payload修改中央if/else；
* Payload复制、析构、异常路径不存在泄漏；
* 现有Native Hole JSON输出语义保持兼容。

增加一个仅用于API无关测试的Synthetic Payload和Synthetic Decoder，证明新增测试Payload时不需要修改：

```text
Crawler
FeatureRecord中央字段
DecoderRegistry核心流程
中央JSON Writer分支
```

不要创建假的NativePadDecoder等生产空类。

## 3. Registry行为补全

现有`ContinueTypedAfterFailure()`不能只声明不用。

必须定义并测试：

* Candidate；
* NotMatched；
* Unsupported；
* Success；
* Partial；
* Exception；
* Rejected；
* Conflict。

明确以下行为：

1. 高优先级Decoder成功后停止；
2. 高优先级Decoder返回NotMatched/Unsupported时继续；
3. Decoder声明允许失败后续尝试时，Registry继续；
4. 不允许后续尝试时，统一回退；
5. 多Decoder成功不得静默覆盖；
6. 冲突必须产生Diagnostic；
7. 同一对象最多只有一个正式Typed Payload；
8. Generic回退不被失败Decoder污染；
9. 统计按decoder_id和结果状态通用聚合，不再只有Hole专项硬编码。

现有Hole统计可以作为兼容视图保留。

# 五、Feature Center统一数据模型

不要把CAA原生Feature、B-Rep区域、视觉候选和融合结果全部塞入同一个模糊JSON对象。

建立以下两层模型。

## 1. Observation

每个数据源独立产生Observation：

```json
{
  "observation_id": "OBS...",
  "part_id": "PART...",
  "source_kind": "native_caa | brep_deterministic | vision_assisted | human_review",
  "source_id": "NativeHoleDecoder | HoleGeometryVerifier | future_provider_id",
  "source_version": "1.0.0",
  "source_config_hash": "...",
  "proposed_family": "hole | rib | web | cavity | island | freeform_surface | unknown",
  "proposed_subtype": "...",
  "native_feature_refs": [],
  "geometry_refs": {
    "face_ids": [],
    "edge_ids": [],
    "wire_ids": [],
    "solid_ids": [],
    "mesh_primitive_ids": []
  },
  "evidence_refs": [],
  "measurement_refs": [],
  "classification_confidence": 0.0,
  "localization_confidence": 0.0,
  "measurement_confidence": 0.0,
  "status": "candidate | verified | rejected | ambiguous | needs_review | unsupported | failed",
  "provenance": {},
  "diagnostics": []
}
```

三个置信度必须分开，不得使用一个0.95掩盖分类正确但定位不准的问题。

本轮的真实Observation只允许来自`native_caa`和`brep_deterministic`。协议Fixture不得写入正式`observations.jsonl`。若未来接入视觉或人工复核，必须新增Observation并引用原候选，不得原地改写历史Observation。

## 2. Canonical Feature

融合后的统一特征至少包含：

```json
{
  "feature_center_id": "FC...",
  "part_id": "PART...",
  "family": "hole",
  "subtype": "counterbore",
  "status": "verified",
  "source_observation_ids": [],
  "native_feature_ids": [],
  "geometry_refs": {},
  "coordinate_frame": {},
  "typed_payload": {
    "payload_type_id": "native_hole",
    "schema_version": "1.0.0",
    "data": {}
  },
  "relations": [],
  "resolution_mode": "deterministic",
  "review_state": "auto_verified | needs_review | user_confirmed | user_rejected",
  "provenance": {},
  "diagnostics": []
}
```

必须支持的关系至少包括：

```text
DERIVED_FROM_NATIVE_FEATURE
SUPPORTED_BY_OBSERVATION
HAS_FACE
HAS_EDGE
HAS_MESH_PRIMITIVE
CONTAINS
ISLAND_OF
ADJACENT_TO
ATTACHED_TO
INTERSECTS
OPENED_BY
POSSIBLE_DUPLICATE_OF
CONFLICTS_WITH
```

`HAS_FACE`和`HAS_MESH_PRIMITIVE`关系必须允许携带role，例如`main_wall`、`bottom`、`counterbore_step`，不能只有无语义ID数组。

`typed_payload`必须通过Payload Schema Registry校验：

* `payload_type_id`全局唯一且版本化；
* `data`按对应Schema验证；
* 未识别的未来Payload可以原样保留并标记Schema不可用，不能导致整个Bundle无法读取；
* Native Hole的Typed Payload字段语义必须与现有`features.jsonl`兼容或提供显式映射；
* Viewer通过Schema/字段描述渲染，不得为每个Payload在中央组件增加硬编码分支。

人工确认或修正不得删除原始Observation，应创建review revision并保留可追溯性。

`resolution_mode`统一使用：

```text
deterministic
vision_assisted
human_reviewed
```

解析终态统一使用：

```text
verified
needs_review
unsupported
failed
```

不得把“是否使用视觉”“是否需要复核”“算法是否失败”混在一个状态字段中。

## 3. ID、不可变性和版本

以下ID不得包含绝对路径、进程ID、生成时间或随机UUID：

```text
part_id
observation_id
feature_center_id
measurement_id
relation_id
```

它们应由规范化输入身份、来源ID、关键几何指纹和算法版本确定性生成。同一输入同一版本双跑必须稳定；算法版本改变时允许形成新ID或Revision，但必须有迁移说明。

Observation一经写入视为不可变。Fusion形成Canonical Feature时保存所引用Observation的Hash。人工复核或未来视觉复核产生新Observation和Canonical revision，不得覆盖历史证据。

所有跨文件引用必须在Bundle Validator中检查：

* 引用对象存在；
* part_id一致；
* Feature引用的Face属于同一Part/Solid上下文；
* Measurement引用的Face存在；
* Mesh映射引用的Primitive和索引范围有效；
* 不允许环状`POSSIBLE_DUPLICATE_OF`之外的非法自引用；
* 失败项保留Diagnostic但不能产生半截Canonical Feature。

## 5. 几何派生关系

### PARALLEL_TO

对平面使用法向夹角；对圆柱/圆锥等解析曲面使用轴向；对自由曲面不得仅用质心法向声称全局平行。

### OPPOSITE_TO


它是后续筋/腹板厚度推理的公共能力，不等价于“已经识别出筋”。

### COAXIAL_WITH

至少适用于圆柱、圆锥和旋转曲面，记录轴线距离残差、轴向夹角残差和半径/锥角信息。Hole映射必须复用这一关系或同一底层计算，不能另写一套不一致的同轴判断。

### NEAR_TO

* 拒绝NaN/Inf；
* 区分主曲率、平均曲率、高斯曲率；
* 对平面、圆柱、球面等解析曲面设置可验证的Ground Truth；
* 对自由曲面只输出由实际采样支持的摘要。

## 8. 稳定ID和指纹

必须处理完全对称或几何同构实体无法唯一排序的情况：

* 在当前Shape内使用确定性拓扑遍历上下文消歧；
* 如果仍存在不可区分的等价类，显式记录`equivalence_class_id`；

跨版本匹配属于后续独立能力，必须使用几何指纹、邻接指纹、装配上下文和匹配算法；本轮不以“稳定ID”名义偷偷实现或承诺跨版本匹配。


## 2. 路由决策

输出只能是：

```text

```

```text

OR topology_validation_status = failed
```

* `NO_REVIEW`不产生请求记录；

* 不生成图片；
* 不读取密钥；
* 不发起网络请求。

`record_only`可以生成`visual_review_requests.jsonl`，但仍不得调用远程服务。`enabled`只预留枚举和配置校验，本轮不得实现实际Provider。


# 十二、未来视觉响应与Face回链协议

本轮只实现严格Schema校验器和离线Fixture，不实现VLM Adapter。未来视觉模型不直接猜Face编号，而是返回视图区域，再通过同相机Face-ID图回链。

```json
{
  "analysis_version": "1.0",
  "request_id": "VR...",
  "part_id": "PART...",
  "candidates": [
    {
      "candidate_id": "VC...",
      "proposed_family": "rib | web | cavity | island | freeform_surface | unknown",
      "proposed_subtype": "...",
      "regions": [
        {
          "view_id": "candidate_iso_001",

      "localization_confidence": 0.0,

      "reason_summary": ""
    }

```

必须校验：

* `request_id`、`part_id`与请求一致；

# 十四、型腔/岛屿所需的eAAG就绪性探针

# 十七、轻量化Mesh和映射

生成GLB或仓库现有轻量化格式。

MVP阶段可以采用“一Face一Primitive”或“共享Mesh但保留连续Triangle Range”，优先保证映射正确。

必须先调查现有轻量化链路和Viewer能力，再选择策略：

* 如果Viewer支持Primitive级拾取，优先一Face一Primitive；
* 如果Primitive数量导致明显性能问题，使用共享Mesh + 明确Triangle Range；
* 不得为了减少文件大小合并到无法稳定反查Face；
* 顶点可以共享，但每个三角形必须唯一归属于一个源Face；
* 曲面离散参数、弦高偏差、角度偏差和相对偏差必须记录到Manifest；
* 法向、三角形绕序和Face orientation必须一致或有显式修正规则。

必须输出：

```text
face_id → mesh_primitive_id/triangle_range
feature_center_id → face_ids
feature_center_id → mesh primitives/triangle ranges
mesh primitive/triangle → face_id
```

不得只靠材质颜色反查特征。

`triangle_range`必须明确单位是索引元素、三角形序号还是字节偏移，推荐使用：

```text
primitive_id
triangle_start
triangle_count
index_start
index_count
lod_id
```

不得让前端猜测`start=36`的含义。

轻量化模型必须：

* 保持单位和坐标；
* 保持装配实例变换；
* 支持Face拾取；
* 支持特征高亮；
* 支持恢复原材质；
* 支持透明、隐藏和隔离；
* 支持剖切；
* 不因LOD导致映射完全丢失。

如果LOD会改变三角形索引，每个LOD必须有独立映射。

映射完整性校验至少包括：

* 每个导出的Face至少对应一个非空Triangle集合，退化或无法离散的Face必须有Diagnostic；
* 每个Triangle恰好反查到一个Face；
* 每个Canonical Hole的所有已验证Face都能反查Mesh；
* 不属于该Hole的Face不得出现在Feature Mesh映射中；
* glTF/GLB实际Primitive数量、Index范围与JSON映射一致；
* 重载页面后拾取结果稳定；
* 双跑映射文件字节稳定。

## Gate 4：Hole → Face

